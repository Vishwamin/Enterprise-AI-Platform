# PHASE.md — Phase 3: Database Foundation

## What was added

- **PostgreSQL** as the project's database (local instance for now).
- `settings.database_url` in `app/core/config.py` — new centralized
  setting, same pattern as Phase 2's `app_env`/`log_level`.
- `app/db/session.py` — SQLAlchemy `engine` (manages the connection
  pool), `SessionLocal`, and a `get_db()` FastAPI dependency for future
  endpoints to use.
- `app/db/models.py` — two SQLAlchemy ORM models:
  - `Organization` (`id`, `name`, `created_at`)
  - `User` (`id`, `email` [unique, indexed], `name`, `organization_id`
    [foreign key -> `organizations.id`], `created_at`)
- **Alembic**, initialized and wired to our `Settings` + model metadata
  (`alembic/env.py`), so `alembic revision --autogenerate` always reflects
  the real `DATABASE_URL` and the real current models — never a
  hardcoded/duplicated URL that could drift.
- `alembic/versions/0001_create_organizations_and_users.py` — our first
  migration, autogenerated, applied and verified against a real local
  Postgres instance. **This file is permanent — future schema changes
  are new migrations (`0002_`, `0003_`, ...), never edits to this one.**
- `tests/conftest.py` — a `db_session` fixture that connects to the real
  database, rolls back after every test (nothing persists), and **skips
  cleanly** (not crashes) if Postgres isn't reachable.
- `tests/test_db.py` — 3 new tests, run against a real Postgres instance:
  - creating an org + user and confirming the relationship works
  - confirming Postgres **rejects** a user with a nonexistent
    `organization_id` (the FK constraint, not application code, enforces this)
  - confirming Postgres **rejects** a duplicate email (the unique
    constraint, not application code, enforces this)
- **18 tests total, all passing.**

## What changed

- `app/core/config.py` — added `database_url` field.
- `requirements.txt` — added `sqlalchemy`, `psycopg2-binary`, `alembic`.
- `.env.example` — added `DATABASE_URL` (fake/local default, no real secret).
- `README.md` — added Postgres setup prerequisites and migration step.

**No breaking changes to existing endpoints** — `/health`, `/`,
`/api/v1/ask` are untouched. All 15 Phase 1/2 tests still pass unmodified.

## Concepts learned

- Tables, rows, columns, primary keys
- Foreign keys as a database-enforced **constraint** (not a copy
  operation) — verified for real with `test_foreign_key_rejects_nonexistent_organization`
- Unique indexes — verified for real with `test_email_must_be_unique`
- Why indexes matter at scale (unindexed lookups scan every row)
- Transactions: used directly in tests — `db_session.flush()` sends
  changes to Postgres (triggering constraint checks) without
  committing, and the fixture **rolls back** afterward, so nothing a
  test does ever persists
- Connection pooling — handled by SQLAlchemy's `engine`, not hand-written
- Migrations: versioned, ordered, reviewable schema changes; **you never
  edit an already-applied migration — you write a new one** (verified
  by actually running `alembic downgrade base` then `alembic upgrade
  head` and confirming the tables cleanly disappear and reappear)

## How to run

```bash
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
# edit .env -> set DATABASE_URL to match your local Postgres
alembic upgrade head
uvicorn app.main:app --reload
```

## How to test

```bash
pytest -v
```

Expected: `18 passed` (if Postgres is reachable) — or the 3 `test_db.py`
tests will `SKIP` with a clear message if it isn't, while the other 15
still run and pass.

Manually verify the schema:
```bash
psql -U postgres -d enterprise_ai_platform -c "\d users"
```

You should see the `organization_id` foreign key constraint and the
unique index on `email`.

## Known limitations

- `User` has no password field yet — authentication is Phase 4
- No `roles`/`permissions` tables yet — RBAC is Phase 5
- No `documents` table yet — Phase 7
- Single migration so far; the real test of "new migration, don't edit
  old ones" comes in Phase 4 when we add a password column
- DB connection details are still all-local; a real deployment would
  point `DATABASE_URL` at a managed Postgres instance via its own
  environment config, never hardcoded here
